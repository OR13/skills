## Brief for the reviewing agent

### Scope
Read `src/issue.ts`, `src/verify.ts`, `src/types.ts`, `README.md`, and `package.json` if present. Fetch `https://www.w3.org/TR/vc-data-model-2.0/` and treat it as the only normative authority; where it defers to VC-JOSE-COSE or VC Data Integrity, fetch those before making a claim about them.

Write nothing. No edits under `src/`, no new files, no `npm install`, no git operations. Report only.

### Hunt for
Seven named failure modes. For each, state present / absent / cannot-determine.

1. **VCDM 1.1 carryover.** `issuanceDate` or `expirationDate` where 2.0 requires `validFrom` / `validUntil`; the `https://www.w3.org/2018/credentials/v1` context; `proof` treated as a required core property.
2. **Required properties absent from the `VC` type.** `credentialSubject` doesn't appear in the type at all; `type` and `issuer` are declared optional (`?:`) where 2.0 requires both.
3. **`issuer` narrowed to `string`.** 2.0 permits a URL *or* an object carrying an `id`. A string-only type makes conformant credentials unrepresentable.
4. **`@context` unpinned.** Typed `string[]`, so nothing enforces that the first element is exactly `https://www.w3.org/ns/credentials/v2`.
5. **Claims spread at the top level.** `issue()` spreading `claims` into the root puts subject claims as siblings of `@context` rather than under `credentialSubject`, leaving unmapped top-level terms. Check separately whether a claim key of `type`, `issuer`, or `@context` silently overwrites the credential's own.
6. **`verify()` cannot return false.** No signature check against any key, no `validFrom`/`validUntil` window check, no `credentialStatus` check. Rate on the assumption it's deployed as a security control.
7. **`key` unused; nothing secures the credential.** `issue()` accepts a key but the output appears to carry no proof and no JOSE/COSE envelope, so nothing binds issuer to claims.

Report anything outside this list under **Additional findings**; don't let the list cap you.

### Must hold
- Every finding cites a VCDM 2.0 section number and quotes the normative sentence. Uncited findings are dropped on arrival.
- Every finding carries **Assertion**: one concrete `expect(...)` line testable against `issue()` output or a `verify()` return.
- Core data model and securing mechanism stay separated. Do **not** report a missing `proof` as a VCDM 2.0 core violation — 2.0 moves securing into VC-JOSE-COSE and VC Data Integrity. Findings 6 and 7 go under a **Securing** heading, labelled with which spec they come from.
- Name at least one thing the code gets right, or state you found nothing conformant. A report where every line is a finding gets re-run.
- Don't infer behaviour from a filename or type signature alone. If a body doesn't settle a question, answer `cannot-determine` and say what you'd need to read.

### Return
```markdown
### <short title>
- **Severity:** blocker | major | minor
- **Location:** path:line
- **Spec citation:** § number + quoted normative sentence
- **What is wrong:** one sentence
- **Why it matters:** the failure it produces in a real exchange
- **Proposed change:** concrete patch
- **Assertion:** expect(...)
```
Close with a table: property | 2.0 requirement | current state | conformant y/n. If nothing is found, return `NO_FINDINGS_DETECTED` and nothing else.

### Order
One phase, three stages: fetch the spec, then read all four files end to end, then write findings. Don't start writing findings while still reading.
