## Plan

- **Problem** — Decide which patches to keep and in what combination, and prove the survivors preserve current behavior, given that with no spec, HEAD's behavior is the only oracle available.
- **Approach** — Fan out in-session with worktree isolation. It beat plain in-session because each reviewer must actually run `make test` against a *different* applied patch and they'd stomp one checkout; it beat separate sessions because the interaction matrix and the merge need to stay with me rather than become four things you watch.
- **Steps** — Phase 0 (me): capture a golden oracle from HEAD. Phase 1 (one worker, blocking): judge `harness.patch` alone. Phase 2 (three workers, parallel): parser, cache, ranking, each applied alone. Phase 3 (me): interacting pairs + all-four. Phase 4: two cold judges.
- **Verification** — `make test` exits zero, and the golden oracle (query → ordered doc ids, captured at HEAD) is byte-identical under the merged tree. Any patch that moves the oracle justifies each changed line or gets dropped.
- **Operator input** — Path to the real repo. Confirm the oracle is the right ground truth. Check your installed skills for a hidden planning/spec skill.

### The ordering constraint — why this isn't four parallel reviews

`harness.patch` rewrites the thing that would verify the other three. It's a measuring instrument until proven otherwise, so it goes first, alone, on unmodified `src/`, and the only question asked of it is whether it reports what the old harness reported.

The other three touch separate files but aren't independent:

| Pair | The bug a per-file reviewer won't see |
|---|---|
| parser → cache | cache keys on raw query string while parser changes normalization → collisions appear or disappear |
| ranking → cache | cache stores *ranked* results → ranking change is masked until eviction |
| parser → ranking | both move result order → each masks the other under an order-insensitive assert |

### Phase 0 — the oracle

No spec means "correct" needs pinning to something. At HEAD, unpatched: capture ordered doc ids, hit counts, and the `make test` verdict for a fixed query set. Every brief below checks against that file. Without it, each brief degenerates into opinion.

## Reviewer briefs

**R0 — harness** *(blocking; nothing dispatches until it returns)*
- **Scope.** Read `tests/harness.py`, `patches/harness.patch`, `Makefile`. Apply only `harness.patch`, in your own worktree. Don't touch `src/`. Report only, don't fix.
- **Hunt for.** (1) Weakened assertions — order-sensitive compare replaced with set/subset, tolerance widened, case skipped. (2) Fixture/seed changes that alter what gets indexed, making old and new incomparable. (3) Tests that no longer execute: renamed out of discovery, collected but not run, exit code no longer propagating to `make`.
- **Must hold.** On unmodified `src/`, patched harness produces the same verdict and same ordered doc ids as the Phase 0 golden. Diff touches only `tests/`.
- **Return.** Standard finding schema + `ORACLE_PRESERVED: yes|no` with diverging queries. Else `NO_FINDINGS_DETECTED`.
- **Order.** Alone, first.

**R1 — parser**
- **Scope.** `src/parser.py`, `patches/parser.patch`, parser callers. Apply only this patch. Don't edit cache or ranking.
- **Hunt for.** (1) Inputs that used to parse and now raise or vice versa — empty, quoted, operators, non-ASCII. (2) Normalization changes that alter output *identity* without altering output *meaning* — invisible alone, breaks the cache. (3) Parser branches the suite never reaches.
- **Must hold.** `make test` zero. Signatures unchanged or all callers updated in the same patch. Oracle unchanged or every delta justified.
- **Return.** Standard schema + `ORACLE_DELTA:` per changed query.

**R2 — cache**
- **Scope.** `src/cache.py`, `patches/cache.patch`, the index call site it wraps.
- **Hunt for.** (1) **Key omits an input that affects the result** — parsed form, filters, pagination, ranking params. Highest-value check in the review. (2) Whether it stores raw hits or ranked output; if ranked, R3's review is unsound under the merged tree. (3) No invalidation / no size ceiling / unbounded growth keyed on user input; staleness with no TTL. (4) Whether the cache is even live during the test run — a bypassed cache is unverified by a green suite.
- **Must hold.** Oracle identical **cold and warm** — run the query set twice in one process and diff the runs against each other. Results that change on the second run are a defect regardless of the suite.
- **Return.** Standard schema + `KEY_INPUTS:` (exact fields composing the key) + `STORES: raw|ranked`.

**R3 — ranking**
- **Scope.** `src/ranking.py`, `patches/ranking.patch`.
- **Hunt for.** (1) Score changes presented as neutral refactors that reorder results — every reordering is a product decision with no spec behind it; flag for you rather than judging. (2) Tie-breaking: equal scores that previously resolved stably and now don't → nondeterminism across runs. (3) Division by zero on empty result sets, negative/NaN scores, overflow on long documents.
- **Must hold.** Three consecutive runs byte-identical. Every oracle delta enumerated, not summarized.
- **Return.** Standard schema + `ORACLE_DELTA:` with before/after ordering.

**Phase 3 — interaction matrix (mine, not delegated).** Four trees: parser+cache, ranking+cache, parser+ranking, all-four. Each gets `make test` plus the cold/warm oracle diff.

**Judges — two, cold, kill mandate.** **J1** reads the merged diff, hunting over-engineering: abstractions with one implementation, passthrough layers, unused knobs, widened surface for a single caller. **J2** never reads the diff — it runs the system and reads what it emits: logs, timings, memory under repeated distinct queries, the cold/warm delta. Different evidence is what makes it a second judge instead of the first billed twice. Each must name at least one finding to drop or return `NO_FINDINGS_DETECTED`. I merge and tell you which judge I overrode.

Single-patch correctness passes route through your installed `/code-review` skill inside each worktree; the briefs cover what it won't — the oracle, the harness-as-instrument problem, the interaction matrix.
