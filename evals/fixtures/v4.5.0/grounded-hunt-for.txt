## This is two problems

| | in this shot | reason |
|---|---|---|
| double refund | yes | check-then-insert with no constraint |
| webhook double-processing | yes | same defect, same fix shape |
| settlement never finishing | **no** | liveness, not exactly-once |

Settlement shares no code and no failure class with the other two. Its modes — unbounded loop, no batching, no resume cursor — are asserted at `tests/test_settlement_drains_under_backpressure.py` and the 45s ceiling in `.github/workflows/ci.yml`, and the fix is throughput work. Bundling a money-table migration with a throughput rewrite produces one diff that can't be reverted in a single commit, which is the wrong property for payments. It waits on one answer: **is 45s a real SLO, and on exceeding it should the run resume from a cursor or fail loudly?**

Sequencing note, not a reason to merge: if W4 moves webhook work off the request path to satisfy ADR 0012, it lands on the same async job path settlement uses.

### W1 — refund path

**Scope.** Read `src/payments/refund.py`, `src/payments/charge.py`, `tests/test_charge_idempotency.py`, and the refund table's schema/migrations. Write nothing.

**Hunt for.**
- **Failure mode:** check-then-insert race — two concurrent calls both `SELECT` no row, both `INSERT`.
  **Property:** a charge refunds at most once per logical refund request.
  **Asserted at:** nowhere. `tests/test_charge_idempotency.py` covers charge only; there is no refund equivalent and no unique constraint. The absence is the finding — confirm it, don't assume it.
- **Failure mode:** no caller-supplied key, so `refund(charge_id, amount)` can't distinguish a retry from a genuine second partial refund.
  **Property:** retries are distinguishable from intent.
  **Asserted at:** `charge(card_token, amount, idempotency_key)` — the sibling API on the same money path takes the parameter. Report what charge.py does on a seen key; W3 copies that shape.
- **Failure mode:** partial refunds summing above the original charge.
  **Property:** total refunded never exceeds amount charged.
  **Asserted at:** nothing in the listing. **This one is a guess** — confirm against the code or drop it.

**Must hold.** Zero files modified. Every finding cites file and line range. Report the exact current `refund()` signature and every call site.

**Return.** Per finding: Location / What is wrong / Why it matters / Proposed change / How to check it. Plus a `Duplicate rows` section: does the refund table currently hold duplicates from the incident? `NO_FINDINGS_DETECTED` if the path is already safe.

### W2 — webhook path

**Hunt for.**
- **Failure mode:** the dedupe check isn't a transactional claim, so two concurrent redeliveries of one event id both pass it.
  **Property:** handlers idempotent, keyed on provider event id.
  **Asserted at:** `docs/adr/0007-exactly-once-webhooks.md` and `tests/test_webhook_replay_rejected.py` — which passes today. **Primary question: explain how that test passes while production double-processed.** Likely it replays sequentially and never concurrently — verify; if the real gap is elsewhere, say so.

  **Property:** no blocking IO in handlers. **Asserted at:** `docs/adr/0012-no-blocking-io-in-handlers.md`. Name the blocking calls; say whether an async job path already exists.

**Must hold.** Zero files modified. Quote the ADR 0007 clause verbatim; don't paraphrase it into a stronger claim.
